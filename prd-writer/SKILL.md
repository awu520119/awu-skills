---

name: prd-writer
description: 当用户要求撰写、新建、补充或修改 PRD 时使用。基于需求资料，严格按照 `reference/prd-template.md` 输出结构清晰、规则明确、可供产品、研发、测试及 AI 读取的 Markdown PRD。
---

## 一、触发词（trigger）

`/prd-writer`

### 触发

* 写 / 生成 PRD
* 根据需求分析生成 PRD
* 补充 / 修改已有 PRD
* 将明确需求整理为 PRD

### 不触发

* 需求分析
* UI 设计
* 技术方案 / 接口 / 数据库设计
* 代码实现

---

## 二、一句话描述（description）

基于已明确的需求信息，严格按照 `reference/prd-template.md` 生成标准 PRD。

核心原则：

> 忠于需求，不脑补；描述业务，不预设技术；一个信息只定义一次。

---

## 三、输入约定（inputs）

| 输入     | 必填 | 说明                             |
| ------ | -- | ------------------------------ |
| 需求信息   | ✅  | 需求分析、已有 PRD 或用户明确提供的需求         |
| 参考 PRD | ⬜  | 仅用于参考表达风格                      |
| 输出目录   | ⬜  | `--output-dir=<dir>`；默认输入文件同目录 |

至少应明确：

* 需求背景
* 需求目标
* 本期功能范围

信息处理：

* 影响核心方案 → 询问用户
* 不影响整体撰写 → 写入「待确认事项」
* 信息冲突 → 以用户最新明确说明为准
* 未明确内容 → 禁止自行假设

---

## 四、执行步骤（steps）

1. **读取需求**
   提取背景、目标、功能范围、业务规则及待确认项。

2. **加载模板**
   读取 `reference/prd-template.md`，以其作为唯一结构和内容粒度标准。

3. **拆分功能**
   按独立业务能力拆分，不按按钮、组件或接口拆分。

4. **建立编号**
   多功能需求使用全 PRD 唯一 `F01、F02...`；重要规则使用 `R01、R02...`；重要验收项使用 `AC01、AC02...`。页面或模块变化后不重新编号。

5. **生成 PRD**
   严格按模板撰写，功能清单与功能详述一一对应；核心业务流程使用 Mermaid。

6. **输出前自检**
   检查功能、规则、交互、状态、异常与验收是否完整、一致、明确，且不存在重复、冲突、模糊描述或未经确认的假设。

---

## 五、输出契约（output）

| 项     | 要求                               |
| ----- | -------------------------------- |
| 格式    | Markdown `.md`                   |
| 模板    | 严格遵循 `reference/prd-template.md` |
| 流程图   | Mermaid                          |
| 功能编号  | 多功能需求使用全局唯一 `Fxx`                |
| 规则编号  | 重要规则使用 `Rxx`                     |
| 验收编号  | 重要验收项使用 `ACxx`                   |
| 待确认内容 | 统一进入「待确认事项」                      |
| 技术实现  | 默认不包含具体技术方案                      |
| 新建文件  | 默认不覆盖原文件                         |

默认文件名：

```text
<需求名称>-PRD-YYYYMMDD.md
```

输出目录优先级：

1. 用户指定 `--output-dir`
2. 输入文件所在目录
3. 无文件时直接输出 Markdown

---

## 六、约束（constraints）

1. **模板唯一**：不得自行增删一级章节，功能详述必须达到模板规定的内容粒度。
2. **禁止脑补**：未明确的信息不得自行确定，必要时进入「待确认事项」。
3. **规则唯一**：同一规则只定义一次，其他位置通过 ID 引用。
4. **编号唯一**：功能 ID 在整个 PRD 内唯一，页面或模块变化后不重新编号。
5. **前后一致**：功能清单、功能详述、业务规则、状态及验收标准不得冲突。
6. **业务与技术分离**：描述产品行为和业务规则，不默认设计数据库、API、架构或代码实现。
7. **口径明确**：涉及金额、比例、数量、时间、状态、配置生效、历史数据、重试等内容时，按模板明确对应口径。
8. **验收可验证**：验收标准必须能够直接转换为测试场景。
9. **禁止模糊表达**：不得使用「按原逻辑」「正常处理」「合理处理」「视情况处理」等无法执行的描述。
10. **禁止强行补全**：无明确要求时，不自行生成性能指标、技术难点、测试用例或技术方案；无内容按模板填写「无」或默认说明。

## 使用示例

### 根据需求分析生成 PRD

```text
用户：
根据 content/结算中心/结算周期-需求分析.md 写 PRD

执行：
读取需求 → 加载模板 → 拆分功能 → 建立编号 → 生成 PRD → 自检 → 输出
```

### 补充已有 PRD

```text
用户：
补充 F03 的异常边界和验收标准。

执行：
读取 F03 及相关规则 → 按模板补充指定内容 → 检查前后一致性 → 其他内容不变
```

### 多页面功能编号

```text
景区商家配置
F01 溢价比例配置
F02 结算周期配置

结算中心
F03 分账失败原因展示
F04 分账失败重试
```

功能 ID 在整个 PRD 内连续，不因页面或模块变化重新编号。
