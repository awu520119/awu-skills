## 适用范围

用于将需求分析、原型标注、已有 PRD 或用户明确说明整理、补充或修订为业务 PRD。不用于需求调研、UI 设计、技术方案、接口/数据库设计或代码实现。

> 忠于需求，不脑补；描述业务，不预设技术；一个规则只定义一次；规则即验收。

## 输入与处理

读取用户提供的需求资料、相关原型和已有 PRD。至少确认需求场景、涉及页面/业务对象及本期功能范围。

- 信息冲突时，以用户最新的明确说明为准。
- 缺失信息会影响方案、研发实现或测试口径时，列入「待确认事项」；不能合理判断时询问用户。
- 未明确内容不得补造为正式规则；参考 PRD 只用于结构和表达风格，不复制无关业务。

## 写作流程

1. 提取需求场景、页面/业务块、字段、状态、动作、边界与待确认项。
2. 读取 `reference/prd-template.md`，以其文档头和按页展开方式为基础；需要时按实际页面增减业务小节，不套用固定页面类型。
3. 按用户操作或业务阅读顺序编排：一个独立页面、抽屉、详情或配置模块对应一个 `##` 章节；同页内存在多个并列业务块时才用 `### 一、…`、`### 二、…` 分组。
4. 将每个字段、展示规则、校验、权限、状态变化和二次确认写成可直接验证的业务口径。
5. 输出前按下方自检项清理注释、示例和占位符。

## 文档骨架

文档头固定为：

```markdown
# <需求名称> PRD

> 版本 v1.0　·　日期 YYYY-MM-DD

*需求场景：<谁在什么情况下，为解决什么问题，需要什么能力。>*

## 变更记录

| 版本 | 日期 | 变更内容 | 提出人 |
| --- | --- | --- |
| v1.0 | YYYY-MM-DD | 初版 | — |

## <页面或业务模块名称>
```

- 需求场景是一句完整的斜体描述，紧跟版本行，不另设章节。
- 一个页面/业务模块一个 `##`；单一业务块可直接从 `1.` 开始，多个并列业务块再用 `### 一、…`、`### 二、…` 分组。章节名称按实际业务命名，例如「筛选项说明」「列表说明」「结算周期说明」「拍摄点分成」。
- 仅在确有未决问题时添加文末 `## 待确认事项`；无内容时不保留空章节。
- 变更记录按版本倒序；首版保留「初版」一行。多页面 PRD 可用 `---` 分隔页面，单页面或连续阅读更清晰时无需强加分隔线。

## 表达与排版

- 正文用有序列表逐条表达规则；同一组内从 `1.` 开始。补充、条件和并列分支缩进 4 个空格，用 `-` 表达。
- 字段、规则、状态和操作采用 `**名称**：说明`；名称后可附「（补充）」而不加粗。父项只有子项时可用 `**名称**：`。
- 选项值、状态值、按钮、页面页签、提示与确认文案均用「」；变量保留为 `{变量名}`，例如「该点分成合计 {合计}%」。
- 条件必须写清触发条件和结果，使用「若…，则…」或「…时，展示…」。金额、比例、数量、时间范围、周期、生效范围、历史数据与重试必须给出口径。
- 三项及以上的状态、枚举、校验或金额构成优先用表格；表格紧随所属条目，表头分隔行统一为 `| --- |`。
- 同一规则只写一处：字段内校验跟字段走；跨字段/跨行校验放在相应业务块；明细行操作跟明细走；跨页面共用口径首次定义后明确引用位置。
- 自动带出、自动计算或自动刷新必须写明数据来源、触发/刷新时机和无结果时的展示或可否继续操作。

## 禁止与自检

禁止使用「按原逻辑」「正常处理」「合理处理」「视情况处理」等不可验收表述；禁止无依据补充技术实现、性能指标或测试用例。

输出前检查：

| 检查项 | 要求 |
| --- | --- |
| 结构 | 文档头、变更记录、页面章节完整；只保留有内容的小节和待确认事项 |
| 口径 | 每条规则可转为测试场景；条件、范围、结果和文案明确 |
| 一致性 | 同名字段、状态、周期和计算公式前后一致；无相互冲突的规则 |
| 清洁 | 无 HTML 注释、示例、`<...>`、未替换日期或独立成行的「无」 |
| 边界 | 未确认信息不写成规则；不包含数据库、接口、架构或代码方案 |

## 输出

默认输出 Markdown 文件，文件名为 `<需求名称>PRD-YYYYMMDD.md`；优先写入用户指定目录，否则使用输入文件所在目录。新建文件默认不覆盖原文件；补充已有 PRD 时只改动用户指定章节及其直接相关规则。
